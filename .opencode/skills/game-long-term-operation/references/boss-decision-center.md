# 老板决策中枢：代替主策 + 运营

> 面向不懂数值的决策者。**结论先行，指标退居证据**。
> 引擎负责精确计算，boss 层负责把计算翻译成"要不要上、要拍什么板、谁去改"。

## 为什么需要这一层

`opsreport` / `judge` / `proanalysis` 的输出是给主策看的：指标 key、加权偏差、精确分数、公式。
老板既不读这些也不需要读。老板的问题是三个：

1. **这个版本能不能上？** → `GO` / `HOLD` / `STOP`
2. **需要我决定什么？** → 拍板项（证据 / 选项 / 建议 / 后果 / 期限）
3. **谁去改、怎么验？** → 执行指令 + 验收标准

`boss` 层把底层引擎的输出转成这三件事。

## 六命令速查

| 命令 | 老板场景 | 输出 |
|---|---|---|
| `boss brief` | 早上 3 分钟看版本 | 一句话结论 + Top3 拍板项 + 最严重问题 |
| `boss decide` | 要正式拍板 / 发邮件 | 完整决策包 + 自包含 HTML 驾驶舱 |
| `boss monitor` | 运营日常盯盘 | 红黄绿灯，逐事务显示当前 vs 目标 |
| `boss duty` | 想知道"主策/运营到底该做什么" | 26 项工作事务矩阵 + 判定标准 + 引擎工具 |
| `boss simulate` | 决策前看后果 | 现状 / 按建议整改 / 放任恶化 三情景健康度 |
| `boss ask` | 自然语言提问 | 从问题识别品类并路由到对应命令 |

## 输出结构（Brief）

```
Call      GO / HOLD / STOP          — 能不能上
Headline  一句话结论（经营语言）       — 为什么
Findings  按加权偏差排序的问题        — 每项：经营语言 + 归属(价值/流动/节奏) + 精确差距 + 后果
Decisions 最多 3 项拍板               — 问题/背景/证据/选项/建议/不做后果/负责人/期限/优先级
Actions   对应执行指令                — 负责人/任务/工具/验收
Duties    26 项工作事务当前状态        — 已接入数值的自动判定，未观测的标 idle
Limits    数值替不了的判断            — 趣味/社交/创意、地区合规、派生基准校准
```

## 指标 → 经营语言（翻译表节选）

| 指标 key | 老板看到的话 | 三问归属 | 可调杠杆 |
|---|---|---|---|
| `retention_d1` | 新用户第二天还愿不愿意回来 | 价值 | 核心循环首次反馈、新手引导 |
| `economy_source_sink_ratio` | 货币产出和消耗是否平衡 | 流动 | 产出阀门、消耗口、回收活动 |
| `monetization_ltv` | 一个用户全生命周期值多少 | 价值 | 留存 × 付费深度、长期内容 |
| `progression_pace` | 玩家升级速度是否符合设计 | 节奏 | 经验曲线、日常投放、体力限制 |
| `content_debt_ratio` | 内容积压是否失控 | 节奏 | 扩产、降低消耗速率、复用内容 |

完整 11 项见 `boss/Translate`。

## 主策 + 运营 工作事务矩阵（26 项）

- **主策划 12 项**：价值基准、战斗数值、成长节奏、商业化定价、抽卡概率、经济系统、
  内容节奏、版本评审、配表规范、满级时间、品类基准、指数守卫。
- **运营 14 项**：次日留存、长期留存、付费转化、付费深度、通胀监控、活动排期、
  内容负债、成长节奏、数据盘点、风险预警、玩家分层、合规检查、版本节奏、反馈闭环。

每项含：`ID / 角色 / 领域 / 事务 / 判定标准 / 引擎工具 / 关联指标 / 当前状态`。
数值可自动判定的（关联指标）由 `Analyze` 填入红黄绿；其余标 `idle`（需补数据或人工）。

## 三问归因与后果

每个问题都归到 **价值 / 流动 / 节奏** 之一，并给出"不处理的后果"。
例如留存偏低 → "用户持续流失，后续付费与内容投入都被浪费"；
通胀偏高 → "货币过剩引发通胀，老玩家资产贬值、经济信心崩塌"。
这让老板不必懂指标也能理解优先级。

## 边界（必须一起报告）

- 数值是**领先指标**，不能替代对趣味性、社交黏性与创意的人工评审。
- 健康度基于 11 项通用指标；品类专属问题用 `catalog strategy` 补充。
- 未知品类由标签派生基准，正式决策前建议用 JSON spec 校准。
- 展示值四舍五入，拍板以精确有理数为准。
- 地区合规（CN 抽卡公示/防沉迷等）用 `catalog strategy -region` 单独核对。

## 实现约定

- `boss` 层**只翻译不改写**引擎：所有数字来自 `ops.EvaluateAny` / `num.Num`。
- 严格 API（未知报错）与宽松 API（自动派生）双轨不变；`boss.Analyze` 走宽松轨。
- HTML 驾驶舱零外部资源、可打印邮件；`decide -html` 生成。
- CLI flag 可放在品类 ID 之后（内部 `reorderFlags` 前置，兼容两种写法）。
